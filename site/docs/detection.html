Guide 04 // detection

How Hacker's Lair knows what is live.

A process ID from launch time is useful but not sufficient. Wrappers exit, Docker owns listeners, and projects can start outside the app. Hacker's Lair combines several local signals and labels uncertainty instead of inventing telemetry.

Detection signals

Command-line matching

The match value is searched in the local process command line. Use a distinctive absolute project path or command token. A weak token such as server.js can match unrelated work and should be avoided.

Port evidence

port, ports, uiPorts, and backendPorts declare expected listeners. A ports array is authoritative: every declared port must be listening before that component is ready. This is the preferred mode for Docker Compose, where the listener may belong to Docker rather than the launched shell.

Launch records

When the app starts a component, it remembers the child process and log file. This enables crash reporting, capped auto-restart, exact logs, detected localhost URLs, and copy-command reproduction. It does not replace listener and command-line checks.

Headless tracking

track: "process" marks workers and other long-running programs that never bind a port. Their process evidence determines status.

Status model

API statusUI stateMeaning
stoppedDormantNo configured live signal remains. The card stays compact and does not show dead telemetry.
startingStartingA launch is in progress but readiness evidence is not complete.
runningLiveThe component has sufficient process or listener evidence for its configured detection mode.
erroredErroredThe last launch or stop failed, a component exited unexpectedly, or the expected readiness signal did not appear.

A target with several components can be partially live. The expanded card identifies component-level state instead of collapsing that situation into a false all-clear.

Detected versus configured ports

  • Detected chips are bright and clickable. They come from a localhost URL announced in logs or a configured port that is currently in the live listener snapshot.
  • Ports chips are muted configuration hints. A dormant project can show these but never claims they were detected.
  • If a target is live only through a listener and no matched process is available, the card shows port-detected instead of a fake or missing PID.

Stop and verification

  1. Run stopCommand in the component working directory when configured.
  2. Terminate the remembered and command-line-matched process tree through the platform layer.
  3. Poll configured processes and ports for up to five seconds.
  4. If any signal survives, keep the target live and report that termination was incomplete.

This is why a Docker component should declare both a graceful docker compose down command and its published readiness ports.

Protected processes

Hacker's Lair marks its own control process and operating-system processes as protected. The Port Signals view does not offer destructive actions against those entries. All termination stays local and explicit; the app does not stop an arbitrary listener merely because a new target wants its port.
